# Results

Every number on this page comes from the logs in [`results/`](results/),
recorded on **19 Nov 2026** on **QNX 8.0** (`QNX qnxvm 8.0.0
2026/10/30-09:10:05EDT x86pc x86_64`). The tables are generated by
`python3 host/results_table.py docs/results`; nothing was typed in by hand.

> **This is QEMU, not real hardware.** QEMU 10.0.13 with **TCG software
> emulation** (no KVM was available on the build host), 4 vCPUs, 1 GB RAM,
> image made with `mkqnximage --type=qemu --arch=x86_64`, on a shared
> 8-core Linux host. It runs the real QNX 8.0 kernel, scheduler and message
> passing, so it shows the mechanism working. It does not measure
> real-hardware timing. Set-up details: [`results/vm-setup.txt`](results/vm-setup.txt).

## Set-up

- Binaries built on the host with `qcc -Vgcc_ntox86_64 -Wall -Wextra -O2`
  (zero warnings), copied into the guest, run as root by
  [`scripts/demo.sh`](../scripts/demo.sh). Each run lasts 30 s, and every
  rogue-on case was run 3 times (r1–r3).
- Timing: critical loop 10 ms @ prio 20; sensor / pressure loop 50 ms @
  prio 15; supervisor @ prio 30 with a 1 ms watchdog and 2 ms grace.
- Rogue: one thread per CPU (4) @ prio 25. THROTTLE demotes offenders to
  prio 5, and ESCALATE demotes them to prio 1.
- **Duty choice (tuning, stated honestly).** The rogue burns *duty* % of
  every 10 ms window. At **85 %** it leaves 1.5 ms per window on each of
  the 4 vCPUs, and the control work mostly fits into that slack, so the
  loop barely misses (local guard-off runs: 0.2 % and 0.9 %, plus one run
  spoiled by a guest stall). Those runs are kept below as a record. The
  headline runs use **100 %**, a process stuck in a busy loop. That is now
  the default.
- **Definitions.** *Judged* means cycles whose deadline has passed
  (completed + starved/skipped). *Miss %* is misses / judged. *Longest
  streak* is the longest run of consecutive misses; × 10 ms it gives the
  outage length. *Supervisor stall* is the longest gap between log rows
  while tasks are active. The prio-30 supervisor logs every 10 ms, so a
  gap of seconds means the **whole guest** stopped (an emulator stall),
  which no scheduling policy can fix.

What this shows:

- **A, guard off:** the runaway process starves the dose loop for the
  **entire 20 s attack** (longest streak 2000–2004 cycles in all 3 runs).
  The pump under-doses by up to **−82 to −87 %** and shows **no alarm**:
  a silent failure. Dose error is still −60 % at 30 s. The motor speed
  limit keeps it from catching up.
- **B, guard on, rogue registered as demotable:** THROTTLE **9–10 ms after
  the first miss** in all 3 runs, and the final dose error is 0.0 %. The
  worst dip was −3.4 % (r1). Later misses (longest 70–150 ms) coincide with
  emulator stalls (see the supervisor stall column). In r3 they also
  triggered ESCALATE.
- **C, guard on, rogue unknown (nothing to demote):** SAFE_STATE **290 ms
  after the first miss** (the 300 ms threshold) in all 3 runs. The
  supervisor boosts the dose thread to prio 29 so it can act. The pump
  stops the motor and latches `ALARM: SAFE STATE (motor stopped by
  guard)`. After the safe state the boosted dose loop keeps
  its deadlines (9–21 miss rows out of ~2770 cycles in the remaining
  ~28 s).
  The pressure loop, which was not boosted, stays starved. The −90 % dose
  error is the therapy stopped *with an alarm*, which is the intended
  fail-safe, unlike A's silent under-dose.
- **C′, guard on, uncooperative rogue named with `--demote-pid`:**
  THROTTLE by pid works without any cooperation from the rogue, and the
  final dose error is 0.0 %. Run r2 hit a bug found in this session: an
  emulator-stall miss at 3.3 s triggered THROTTLE and ESCALATE *before*
  the rogue had created its burner threads. With the fix, the supervisor
  re-checks the pid every 50 ms and logged `pid … has 4 new thread(s):
  demoted to prio 1` at 4.04 s. Before the fix, the same situation ended in SAFE_STATE. That run
  is kept in [`results/pre-fix/`](results/pre-fix/).
- The C′ set was re-recorded after that fix, which only touches the
  `--demote-pid` path. A, B and C ran with the same binaries apart from
  that change.
- +0.0 % final dose error: delivered can lead the wall-clock prescription
  by one 10 ms motor step (+0.02 %).

## Problems seen during recording

- **One guest hang.** At about 15:48 WAT the whole guest stopped
  responding, right after `local-d100-guard-on-r2` printed its summary
  (no ssh, host CPU pinned at 400 % for about 25 min). The VM was reset,
  and the whole local 100 % set was recorded again from scratch. The
  cause was not identified. Together with the 6.2 s and 37.7 s stalls
  above, it points at the TCG emulator on a shared host, but that is not
  proven.
- **QNX behaviour worth knowing.** A process whose threads sat at a low
  `SCHED_FIFO` priority while their own peers spun at 100 % could not be
  removed even with `kill -9`. It went away once its threads were lowered
  to prio 1 with `slay -P 1r -T`. This led to the dw-rogue fix (burners
  stop themselves at the end time).
